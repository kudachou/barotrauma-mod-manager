# 代码审查子代理 —— 通用模板

> 用途：把这份文本作为 prompt 派给一个子代理，让它做**只读**代码审查。
> 配套：`docs/agents/code-review-barotrauma-addendum.md`（本仓库专用附加约束）。
> 模型：如果你想用 GPT-6 Astra 跑审查，见文末「模型选择」。

---

## 0. 怎么用

1. 复制下面「1. 任务简报」整段。
2. 把 `<目标仓库绝对路径>` 和 `<审查视角>` 替换掉。
3. 需要多视角时，用 `workflow` 一次派多个子代理（每个换一个视角），最后按本模板的产出结构汇总去重。

**一次派一个视角**比一次派「什么都查」质量高得多：审计范围越窄，取证越扎实，误报越少。

可选视角（挑 2–4 个）：

| 视角 | 查什么 |
| --- | --- |
| architecture | 模块边界、依赖方向、循环依赖、不合理耦合、重复实现 |
| correctness | 错误处理、空值、并发、边界条件、资源泄漏、数据破坏风险 |
| tests | 覆盖缺口、脆弱测试、缺失的异常路径、假通过 |
| security | 输入验证、命令执行、路径遍历、敏感信息、权限与协议边界 |
| performance | 热路径、无谓全量重算、内存增长、N+1 式 IO |

---

## 1. 任务简报（复制这一段给子代理）

```text
你是资深代码审查员，对 <目标仓库绝对路径> 做一次**只读**审查，视角是：<审查视角>。

【绝对只读】禁止创建、修改、删除任何文件；禁止执行任何会写入的命令（不要跑格式化、
不要跑构建、不要跑会改文件的测试）。只能用读取与搜索手段。所有结论必须来自你实际读到的源码。

【先取证再下结论】
- 先搜索建立事实（例如：所有 child_process 调用点、所有 JSON.parse、所有路径拼接、
  所有 IPC/接口注册、所有 catch 块），再逐个打开文件确认上下文。
- 禁止凭文件名或函数名猜测行为。
- 不确定的事不写进结论；宁可少报，也不要报「可能……」

【只报真问题】不要报风格偏好（缩进、命名喜好、注释多少、目录组织的美观）。
只报影响正确性、安全性、可维护性的实际缺陷与风险。

【每条问题的必填字段】
- title：一句话说清「什么坏了 / 会导致什么后果」
- severity：critical | high | medium | low（判定标准见下）
- file：仓库相对路径，用正斜杠
- line：行号或行号范围；确实无法定位时填 "n/a"
- evidence：你实际读到的关键代码 1–3 行，**逐字引用**（可截断），不要转述
- recommendation：具体可执行的修法（改哪个文件、加什么校验、用什么替代写法）

【严重程度判定】
- critical：可被触发且会造成数据丢失/任意代码执行/任意文件读写。
- high：常见路径下会出错、会破坏用户数据、或有真实可利用的安全缺口。
- medium：边界条件下出错、错误被静默吞掉、性能或资源问题、测试盲区。
- low：可维护性/可诊断性瑕疵，不影响当前正确性。

【产出格式】最多 8 条，按 severity 降序。用 JSON 返回，结构：

{
  "category": "<审查视角>",
  "issues": [
    {
      "title": "...",
      "severity": "high",
      "file": "src/foo.ts",
      "line": "42-58",
      "evidence": "...",
      "recommendation": "..."
    }
  ],
  "notes": "你检查了什么、哪些看似可疑但核实后不是问题（写清楚，便于复核者跳过）"
}

notes 里请务必列出「核实后判定为非问题」的项——这能省掉复核者大量重复劳动。
```

## 2. 汇总者要做的（你自己，不是子代理）

拿到多路结果后按这个顺序处理：

1. **保留 null**：某路失败的，状态记 `failed`、条目留空，**不要重试**、不要替它编内容。
2. **去重**：以「文件路径 + 规范化标题」为键合并。命中时取更高的 severity，合并 evidence 与 recommendation。
3. **排序**：severity 降序；同级按 安全 > 正确性 > 架构 > 测试 > 性能 排。
4. **截断**：按重要性取前 N 条（建议 15），并**明确报告被截断了多少条**，否则读者会以为清单已完整。
5. **复核**：至少对 `critical` 与排名靠前的 `high` 自己打开源码确认一遍——子代理会误报，转述前必须核实。

## 3. 模型选择（GPT-6 Astra）

`subagent` 工具本身**没有 model 参数**，模型选择走设置文件。要让子代理可选用 GPT-6 Astra：

```yaml
# ~/.dsh/settings.yaml
subagent-model-selection:
  enabled: true
  allowedModels:
    - provider: openai        # 必须与 llm-pi-ai.providers 下的路由键一致
      model: gpt-6-astra
```

要点：
- `provider` 填的是 `llm-pi-ai.providers` 的**字典键**（如 `openai`），**不是**插件名 `llm-pi-ai`。
- 该设置在每个新会话组班子代理工具时采样一次 —— **改完要开新会话**才生效。
- 它只决定「可选项里有哪些」；实际用哪个模型由界面上的模型选择器决定。
- 想恢复默认：把 `enabled` 改回 `false`（`allowedModels` 留空）。

## 4. 反面清单（这些做法会让审查变成噪音）

- ❌ 让一个子代理同时查架构+正确性+安全+测试 ⇒ 每项都浅，取证不足。
- ❌ 接受「可能存在问题」「建议检查一下」这类没有证据的条目。
- ❌ 把子代理的结论直接转述给用户而不复核 ⇒ 误报会损伤信任。
- ❌ 因为某路失败就重试到成功 ⇒ 浪费时间；留 null 并如实报告更诚实。
- ❌ 只给「前 15 条」而不说被截断了多少 ⇒ 读者会低估问题总量。
